# 04. 內容深度標準與結構化處理

Canonical for depth & structure standards.

---

## 8.1 深度檢核六維度

每篇文章必須達到以下標準：

| 維度 | 最低要求 | 舉例 |
|------|----------|------|
| 具體數據 | 至少 5 組可驗證數據點 | 營收、成長率、市佔率、用戶數、估值 |
| 時間線 | 關鍵事件附精確日期 | 「2026 年 2 月 27 日」，不是「近期」 |
| 多方觀點 | 至少引用 2 位具名人物或機構 | CEO 發言、分析師報告、對手回應 |
| 因果鏈 | 每個主張要有可追溯邏輯鏈 | A → B → C，附數據 |
| 比較表格 | 涉及多主體時用表格 | 欄位要有具體數據，不要「較強」「較弱」 |
| 商業結構 | 超越表面營收 | 毛利率、客單價、留存率、收入結構占比 |

## 8.2 社群素材補強規則

社群貼文資訊密度低（一則 tweet 可能只有一個觀點、零數據）。改寫時必須：

- 把原貼文核心觀點當作「論點假設」，用數據和案例驗證或反駁
- 補充原貼文沒提到的背景脈絡、時間線、商業結構
- 原貼文有數據時查證後保留；沒數據的主張要自行補上可驗證的數據支撐
- 多個社群貼文可合併成同一主題，但每個觀點都要獨立驗證
- 原貼文引用的數據或報告，追溯到原始來源並直接引用原始來源（不引社群貼文本身）

## 8.3 長度判斷

長度由標題承諾和內容完整性決定，不是字數目標。

| 標題性質 | 預期長度 | 判斷依據 |
|----------|----------|----------|
| 單一概念解釋 | 800–1,500 字 | 定義 + 原理 + 應用場景 + 一個案例 |
| 比較型 | 1,200–2,000 字 | 各自定義 + 核心差異 + 適用情境 |
| 操作指南 | 1,500–2,500 字 | 步驟 + 注意事項 + 常見問題 |
| 深度分析 | 2,500–4,000 字 | 現況 + 驅動因素 + 多方觀點 + 預測依據 + 商業結構 |
| 列表型 | 每項 100–200 字 | 名稱 + 特色 + 適用情境，不灌水 |

**停止條件（符合任一就收尾）**：
1. 論點完整了
2. 開始重複（換個說法講一樣的事）
3. 偏離主題
4. 同一論點已經有 2 個以上案例

## 9.1 內容清理

**必須移除**：
- 引用標記、Perplexity logo
- `<div style="text-align: center">⁂</div>` 之類的裝飾元素
- 空 `<div>` 包裝
- 「Based on the search results,」機器式開頭
- 重複或冗餘段落
- 社群平台 UI 殘留（導航、「Follow」「Like」按鈕文字、廣告、推薦貼文）

**標題層級下移**：H1→H3、H2→H4、H3→H5，依此類推。

## 9.2 連結建置

**內部連結一律走 Tenten Content Index MCP** — 完整流程、政策與錯誤處理見
`11-link-building-mcp.md`。不再使用任何 CSV 或本地快照清單。

摘要：草稿完成後，`quota_report()` 預檢一次，再對整篇草稿呼叫 `plan_links`
**恰好一次**（中文 `locale: "zh"`、英文 `locale: "en"`），依回傳 `edits` 的精確
span 由後往前套用。每篇 3–5 個內部連結，同語言、不自連、同一目標只連一次，
anchor 自然融入原句。`status=partial` / `no_match` 且 `retryable=false` 是正常
終止結果，接受較少或零連結。

**外部連結**：

要加連結：
- 所有英文人名、產品、公司名稱（首次出現時）
- 每個關鍵字只連結一次

不加連結（太知名）：
- 公司：Google、Apple、Tesla、Amazon、Meta、Facebook、Nvidia、AMD、Disney、Microsoft
- 產品：Chrome、YouTube、Instagram、Pinterest、Spotify、Edge Browser

英文版沿用中文版的連結策略，但內部連結要對英文草稿獨立跑一次 `plan_links`。

## 9.3 權威引用與 E-E-A-T

文末加高公信力引用：

**來源標準**：
- Domain Authority (DA) 80 以上
- 類型：頂級大學學術機構、頂級顧問公司（McKinsey、BCG、Bain）、知名創投、政府機關、NGO、一級財經媒體（Bloomberg、CNBC、The Information、Reuters）

**品質要求**：
- 每個引用都要有可點擊的完整 URL，不能只列機構名
- 深度分析文章至少 4 個，一般文章至少 3 個
- 引用要跟文中具體主張對應——不做裝飾性引用
- 不確定某研究報告是否存在就不引。少引一個好過造假

**社群貼文**不算高 DA 來源，不能替代權威引用。追溯到原始來源。

**呈現格式**：
```
- [Bloomberg — Article Title](https://full-url)
```

## 9.4 作者資訊與 CTA

**作者署名**：
- 原始內容有 Tenten.co 作者資訊就保留
- 整合到文章底部

**作者觀點**（文末）：
- 要有專業洞見，不泛泛而談
- 要有具體實務經驗佐證：「我們在 2025-2026 年間協助 X 家企業導入…」
- 提出獨立判斷：不重述文中結論，而是基於實務經驗提出文章沒涵蓋到的洞察

**CTA 規範**：
- 連到 https://tenten.co/contact
- 自然融入結尾，無推銷感
- 跟文章主題有關聯
- CTA 前一句具體說明 Tenten 在該主題的相關經驗（不空泛）

**CTA 範例**：
> 我們最近協助金融和製造業客戶評估 Claude Code 跟 GitHub Copilot 的導入策略，透過試點專案驗證開發效率提升了 20-40%。如果你想討論生成式 AI 在你的企業怎麼用，歡迎跟 [Tenten 團隊預約諮詢](https://tenten.co/contact)。

## 9.5 術語一致性鎖定（長稿件特別重要）

處理超過 3,000 字的稿件時必須執行：

1. 第一遍掃描，列出所有「專業術語、人名、地名、品牌名、縮寫」
2. 為每個術語選定一個正式譯名（首見處附原文，如：人工智慧（artificial intelligence, AI））
3. 全文搜尋替換，避免同一個概念出現多種翻譯
4. 製作術語表附在稿末（學術稿件強制；其他可選）

**常見不一致範例**：

| 錯誤 | 正解 |
|------|------|
| 同篇出現「人工智慧」「人工智能」「AI」三種 | 首見「人工智慧（AI）」，後續一律用「AI」 |
| 「使用者體驗」「用戶體驗」並用 | 統一「使用者體驗」 |
| 「機器學習」「機械學習」並用 | 統一「機器學習」 |
